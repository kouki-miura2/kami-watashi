# apps/backend

- Hono, runtime-agnostic: routes, middleware, services, repositories and DAO interfaces, with no entrypoint and no runtime-specific APIs or dependencies (type-checked against web-standard `webworker` lib types only). It runs through a runtime package (`apps/backend-*`, listed in the root `AGENTS.md`) that imports it and owns the entrypoint; see that package's `AGENTS.md` for runtime-specific rules (secrets, dev/deploy, datastore DAOs).
- Request handling is layered: route (`src/route/*.route.ts`) → service (`src/service/*.service.ts`) → repository (`src/repository/*.repository.ts`) → DAO (`src/dao/*.interface.ts`; the implementations live in the runtime package's `src/dao/`). A route depends only on a service; a service holds business logic and orchestrates one or more repositories, and is the only layer that decides "not found" / validation outcomes; a repository maps a DAO's raw storage shape to a domain entity; only the DAO layer talks to a datastore, and it does so behind an interface so each runtime package can wire in its own DAOs without touching service/repository/route code. Topics are the simplest complete example of the chain: `src/route/topics.route.ts` → `src/service/topic.service.ts` → `src/repository/topic.repository.ts` → `src/dao/topic.interface.ts` → `apps/backend-worker/src/dao/topic.d1.ts`, each with its co-located test.
- No in-memory DAOs: the only runtime is Cloudflare Workers, and `wrangler dev` simulates D1/R2 locally, so a second DAO implementation would only duplicate code. Tests at every layer use hand-written fakes of the interface directly below (DAO fakes for repositories, repository fakes for services, service fakes for routes).
- DAO methods are cut per operation, not per table: a write that touches several tables (plus its history row) is one DAO method, so the runtime implementation can run it as one atomic unit (D1 `batch()`).
  - History: the service decides the `HistoryEntry` (`src/repository/history.repository.ts`), the repository maps it with `toHistoryRecord`, and the DAO writes that row in the same batch as the operation.
  - A write that violates a UNIQUE constraint throws `UniqueConstraintError` (`src/dao/errors.ts`) from the DAO; the service maps it to an outcome (e.g. `name_taken`). Services still pre-check for a friendly error — the constraint covers concurrent requests.
- Routes: one Hono sub-app per resource in `src/route/<name>.route.ts` (`create<Name>Routes(deps)`), chained into the app in `src/app.ts` with `.route('/<path>', ...)` — chaining keeps the Hono RPC types intact. `src/app.ts` itself only holds the cross-cutting middleware (CORS, audit log, auth guard), `onError`, and the chaining; no endpoint handlers.
- Request validation: `@hono/zod-validator` (`zValidator('json' | 'query' | 'param' | 'form', schema)`) on each route, which also gives Hono RPC the request types. Schemas check shape and input limits (from `LIMITS` in `utils`); business rules (uniqueness, ownership, quotas) stay in the service.
- `src/app.ts` exports the Hono app instance's type (`AppType`) for Hono RPC. This is the API contract — no hand-written request/response types.
- Audit logging: every request is logged at the default `"info"` level as a start/end pair of JSON lines (`{ timestamp, level, message: "request started" | "request completed", requestId, method, path, user, status, durationMs }` — `status`/`durationMs` only on the "completed" line, `user` being the authenticated user id or `"anonymous"`), joined by a per-request `requestId` (`c.set('requestId', ...)`, an 8-hex-char id from 4 random bytes — short enough to scan by eye, not a full UUID) since concurrent requests to the same method+path would otherwise be indistinguishable in the log stream. This middleware wraps the auth guard, so a rejected (401) request is logged too, not just successful ones, and it's on by default, not opt-in, so it can't be silently disabled by lowering the log level.
- Auth guard: on in every environment, including local (see `apps/backend-worker/AGENTS.md` for signing in locally). It applies to every route except the exact paths in `PUBLIC_PATHS` (`src/app.ts`), passed as `AppDependencies.auth.excludePaths`. The check follows the same interface-plus-swappable-implementation shape as the DAO layer, but lives outside the service/repository/DAO chain since it's a cross-cutting concern (`src/repository/auth-guard.interface.ts`). The real implementation is `auth-guard.token.ts`: `Authorization: Bearer <credential>`, where the credential is an owner's session JWT or an invited member's key (`mk_...`, stored only as a SHA-256 hash), and the member row is looked up on every request so deleting a member or family revokes access immediately. Routes read the caller with `currentUser(c)` (`src/route/context.ts`).
- After the guard: members who haven't agreed to the current terms get `403 terms_required` (except `TERMS_EXEMPT_PATHS`), and every response without its own `Cache-Control` gets `no-store`.
- Errors: services throw `AppError(code)` (`src/service/errors.ts`); `onError` in `src/app.ts` is the only place that maps a code to an HTTP status, and renders `{ error: code }`. Anything else becomes a logged `500 internal_error`.
- `/dev/*` (local sign-in) is mounted only when `AppConfig.devLogin` is on, outside the typed chain (not part of `AppType`), and refuses non-local hostnames.
- Route tests go through `createTestApp` (`src/testing.ts`), which builds the real app with a fake guard and fakes only the services the test needs.
