# apps/frontend

- A web app (SPA) for phone browsers, installable to the home screen (PWA), served by the same Cloudflare Worker as the API (`apps/backend-worker`) (`docs/spec.md`「提供形態」「アーキテクチャ」). No native app and no Capacitor: device features use plain browser APIs.
- Vue 3 (Composition API, `<script setup>`).
- Vuetify 4 for UI components and theming. The theme (`src/plugins/vuetify.ts`) holds the app's colors; use its color names (`primary` ink, `secondary` vermilion, `link`, `todo`/`done`, ...) instead of raw hex values.
- vue-router for routing. The route table lives in `src/router/routes.ts`, separate from `src/router/index.ts` (which builds the actual `router` with `createWebHistory()`), so tests can import `routes` without pulling in a browser-only history. Route `meta` drives the app shell: `tab` shows the bottom navigation and `noAppBar` hides the app bar (the app's name and the member's) (`App.vue`), `public` marks screens usable signed out (signed-in devices are sent home), `anyone` screens usable signed in or out alike (the terms and privacy policy), `ownerOnly` owner-only screens — the `beforeEach` guard (`src/router/guard.ts`) enforces the last three.
- TanStack Query (`@tanstack/vue-query`, `VueQueryPlugin` installed in `src/main.ts`) for server state — see State below.
- API access goes through a Hono RPC client (`hc<AppType>()`), built from a type-only import of `apps/backend`'s `AppType`. This gives full request/response type inference without a shared types package or manually written DTOs. `src/api/client.ts` sends the credential cookie (`credentials: 'include'`: the API is another origin on the same site; the cookie is HttpOnly and set, renewed and cleared by the API, so this app never sees or stores a credential), times requests out (a slow one, like a photo upload, passes its own `init.signal`), and throws an `ApiError` (`src/api/errors.ts`) for every non-2xx response or network failure — so a resolved call is always a success, and composables don't check `res.ok`.
- Errors are reported in one place: the `QueryCache`/`MutationCache` `onError` in `src/main.ts` calls `createApiErrorHandler` (`src/api/error-handler.ts`), which signs out on `unauthorized` (member → `removed` screen, owner → `welcome`) and otherwise shows the error's Japanese message (`errorMessage`) in the snackbar. A query/mutation that shows its failure itself (inline, in a dialog) sets `meta: { handlesError: true }` to skip the snackbar. Don't `watch` `error` to notify.
- `POST /launch` is a query (`useLaunchQuery`, subscribed in `App.vue`): it first runs at startup (`loadSignIn` in `src/main.ts`, before the router's first navigation — only the API knows whether this browser is signed in) and again whenever the app comes back into view (TanStack Query's default `focusManager`, on `visibilitychange`), renews the credential cookie, and is where `me` comes from. Don't put `me` in a store.
- Query keys: every query key starts with a prefix from `queryKeys` (`src/composables/query-keys.ts`), and a mutation's `onSuccess` calls `invalidate(client, [...])` with every prefix whose data it changes. Composables for one resource live together (`useChildren.ts`: its query and mutations).
- Back/close buttons use `useBack(fallback)` (previous screen, or `fallback` when opened directly). Deletions ask through the `confirm` store; adding/renaming a child or topic goes through `NameDialog` + `useNameEditor` (the dialog shows the failure, so those mutations set `handlesError`).
- Device features are wrapped in `src/device/photos.ts` (take/choose photos through the browser's file picker — `capture` for the camera — already optimized per the spec: downscaled, WebP — natively, or through `@jsquash/webp` (WebAssembly, loaded on demand) where the browser can't encode WebP (Safari) — EXIF dropped; the pure size math lives in `src/lib/photos.ts` so it can be tested) and `src/api/google-sign-in.ts` (Google Identity Services: renders Google's own button, the only way to get an ID token on the web). A user backing out of the picker resolves `[]`, not an error. Pickers open only from a tap: call them right in the click handler, with no `await` before. Uploads pass a longer `init.signal` timeout (`usePrints.ts`).
- PWA (home screen): `public/manifest.webmanifest` and the icons in `public/` (`icon.svg` is the source; `icon-192.png`, `icon-512.png` — also the maskable one, the notice sits in the safe zone — and `apple-touch-icon.png` at 180px are rendered from it). No Service Worker (spec 対象外): Chrome's install criteria no longer need one. The settings screen's 「アプリをインストール」 goes through the `install` store: Chrome's `beforeinstallprompt` (captured at startup in `main.ts`) where offered, otherwise the manual steps (Safari has no install API). After changing `icon.svg`, re-render the PNGs, e.g. with Chrome: `chrome --headless=new --window-size=512,512 --force-device-scale-factor=<size/512> --screenshot=<file> <icon.svg URL>`.
- Joining: the invite QR code (`InviteView`) carries the invite URL `/join?invite=<invite token>` (`src/lib/invite.ts`). The person joining reads it with the app's own scanner (`JoinView` + `QrScanner`: the camera through `getUserMedia`, decoded with `jsqr` — Safari has no `BarcodeDetector`), or opens it from their phone's camera; either way `JoinView` goes on with the token and takes it out of the address bar. The camera needs https (or localhost).
- Settings of your own environment never go in a tracked file (this is a public repository): they go in gitignored `.env.local`. `.env` documents each one.
- Build-time settings (`import.meta.env`): `VITE_API_BASE_URL` (default `/api`: the API on the web app's own origin — deployed, one Worker serves both; in development, the Vite dev server proxies `/api` to `wrangler dev`, see `vite.config.ts`), `VITE_GOOGLE_WEB_CLIENT_ID` (unset → the Google button stays disabled; sign in locally through the welcome screen's development login), `VITE_OPERATOR_NAME` / `VITE_CONTACT_EMAIL` (in the terms and privacy policy; unset → placeholders).
- Terms of use and privacy policy: the texts live in `src/legal/documents.ts` (built from `LIMITS`, so the numbers follow the code) and `LegalView` (`/legal/terms`, `/legal/privacy`) shows them. The agreement step (`TermsAgreement`: registering, joining, a revision) opens them in a new tab, so the step in progress isn't lost; settings opens them in the app. Revising either text means bumping `TERMS_VERSION` (`src/terms.ts` and the API's `wrangler.jsonc`) so every member agrees again.
- Layout pieces: `TabPage` (a tab's top-level page with its large title), `SubPageBar` (the app bar of a screen below the tabs, with a back/close button the parent handles), `StepLayout` (a full-height screen with its main action pinned to the bottom). Stack content inside `StepLayout`, not in a `flex-grow` flex column: Vuetify's block buttons and inputs are flex-grow items and would stretch to the free height.
- Offline, `App.vue` shows the banner and makes the whole screen `inert`, and TanStack Query's `onlineManager` (the browser's `online`/`offline` events) pauses requests; `src/stores/connectivity.ts` mirrors it — screens don't check connectivity themselves.
- TypeScript is pinned to `^6.x` here, independent of the workspace catalog's `^7.x`: `vue-tsc`/Vue Language Tools can't type-check `.vue` SFCs against TypeScript 7's native compiler yet (no public Program API). Re-sync to the catalog once vue-tsc supports it.

## State

State is split by kind — don't reach for Pinia as a catch-all:

- Server state (API responses, caching, fetching/loading/error) goes through TanStack Query (`@tanstack/vue-query`) via `useQuery`/`useMutation`, each wrapped in its own composable under `src/composables/` (`useXxxQuery.ts`) rather than called inline in components. After a mutation, prefer `queryClient.invalidateQueries` over manually patching local arrays to stay in sync. Never store API response data in a Pinia store.
- Pinia (`src/stores`, one store per domain) is for global UI state only — auth info, theme, notifications, and other state shared app-wide that isn't server data. Define stores with the setup-function style, not the Options style, and don't call `fetch`/`axios` from inside a Pinia action; that's TanStack Query's job. Stores: `auth` (whether this browser is signed in, as the owner or a member — the API's answer, from `loadSignIn` at startup and the launch query in `useLaunchQuery.ts`; `localStorage` keeps only that role, as a fallback when offline at startup), `connectivity`, `notification` (the snackbar), `confirm` (`await confirm({...})` opens the shared confirmation dialog and resolves `true`/`false`), `install` (installing to the home screen, see PWA above).
- Local/component state (modal open/closed, form inputs, per-component derived values) stays in composables or component `ref`s — don't promote it to Pinia just because it's convenient.
- Don't destructure values out of `props` or a `reactive` object; it breaks reactivity. Use `toRefs()` or `toValue()` instead. Default to `ref()` for single values, `reactive()` only for grouping related fields (e.g. a form's values), and `ref()` when in doubt.
- When sharing state via `provide`/`inject`, type the key with `InjectionKey<T>` and expose access through a composable (e.g. `useMyContext()`) instead of calling `inject` directly at each call site.

## Testing

Tests run in Node (no jsdom/happy-dom), so keep test subjects DOM-free — test composables, stores, router config, and API wiring directly rather than mounting components. Run with `vp test` / `vp run frontend#test`.

- API client (`src/api/client.test.ts`): spy on `globalThis.fetch` and assert the request (`credentials`, headers, signal) and the thrown `ApiError`.
- Pure functions (`src/lib/*.test.ts`): wording and formats follow the spec's examples verbatim — `history.test.ts` checks every row of the spec's "履歴 > 表示例" table.
- Pinia stores (`src/stores/*.test.ts`): call `setActivePinia(createPinia())` in `beforeEach`, then `useXxxStore()` and assert directly — no app mount needed. Stub the browser globals a store uses with `vi.stubGlobal` (`localStorage` in `src/stores/auth.test.ts`).
- Query composables (`src/composables/use*Query.test.ts`): `vi.mock` `../api/client.ts`, then run the composable inside `effectScope().run(...)`, passing an explicit `queryClient` (a plain `new QueryClient(...)`, `retry: false`) as the composable's second argument instead of installing `VueQueryPlugin` on a mounted app. Await state changes with `vi.waitFor(() => expect(query.isSuccess.value).toBe(true))` rather than a fixed delay.
- Router (`src/router/routes.test.ts`): build a throwaway router from the exported `routes` with vue-router's `createMemoryHistory()` (no real browser history needed), and assert with `router.resolve(...)` rather than `router.push(...)` — `push` actually loads the matched route's lazy component, which drags in Vuetify's CSS and breaks under Node's module loader. The guard is a plain function (`resolveNavigation`), tested with resolved locations and a fake auth state (`src/router/guard.test.ts`).
